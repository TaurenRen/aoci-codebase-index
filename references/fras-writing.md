# FRAS v2 条目写作规范

## 一、条目形态

```
文件名[标签]: F:职责 | R:必须一起读的关联 | A:对外契约 | S:不可推断但改错会出事的约束
```

- `文件名`：basename，带扩展名，不带路径
- 四个字段顺序固定：**F → R → A → S**
- 分隔符是 ` | `（前后各一个空格）
- 一条一行

## 二、标签（compact）

格式声明：`A+B+C+[D]+E`

### 各位取值

| 位 | 含义 | 取值 |
|---|---|---|
| A | Layer 层 | A-应用编排 C-共享基础 D-领域逻辑 E-入口边界 F-声明配置 I-集成适配 K-算法计算 L-库与SDK M-中间件 O-运维交付 P-持久化 R-运行基础 S-文档规范 T-测试验证 X-开发工具 Z-其他 |
| B | Module 模块 | A-分析智能 B-核心业务 C-配置策略 D-数据状态 E-扩展插件 G-跨域通用 H-硬件设备 I-身份权限 L-本地化 M-消息事件 N-网络协议 O-可观测性 P-性能资源 Q-质量保障 R-可靠性恢复 S-安全隐私 U-用户交互 V-构建发布 W-流程调度 Z-其他 |
| C | Importance 重要性 | 9 最高 … 1 最低 |
| D | Trait | 当前 Meta 字典未声明 `-`，**省略** |
| E | Scale 规模 | L 大(>400行) M 中(200-400行) S 小(100-200行) T 微(<100行) |

### 实测要点

- **标签是 4 个字符**。`main.go[EG7T]` 是官方给出的正例。
- 中间插 `-` 会被拒：`object_tag_dictionary_violation`，cause 写明 `D Trait value - is not declared by the current Meta dictionary`。
- **模块位（第 2 位）不能用 `F`**。写配置文件（小程序组件声明 json 之类）用 `C`。

### 自动纠正写法

```python
letters = [c for c in tag if c.isalpha()]
digits  = [c for c in tag if c.isdigit()]
tag = letters[0] + letters[1] + digits[0] + letters[-1]   # 4 位
```

## 三、四个字段

### F（Function 职责）

一句话说清这个文件负责什么、在系统里是什么角色。
写"干什么"，不写"怎么实现"。不要复述代码。

### R（Relationships 关系）

理解它必须一起读的其他文件。

- 格式**只能是** `code:相对路径`
- 多项用英文逗号分隔，**不要空格**
- 没有强关系写 `-`
- **禁止**自然语言（不许写"调用了 XX 模块"）

### A（API 对外契约）

外部调用方依赖它的什么。

- 逗号分隔的标识符列表
- 函数/方法名、组件名、properties 名、`triggerEvent` 事件名、导出对象、配置项
- 没有对外契约写 `-`

### S（Stability 稳定性约束）

**最高价值也最容易写坏的一条。**

准入标准（两条都要满足）：

1. **不可推断**：看代码看不出来，是外部事实或跨文件隐式约定
2. **能防错**：改的人不知道就会踩坑

典型的合格 S：

- 某处写死了这个组件的宽高，改它会连带崩版式
- 这个开关只在生产环境生效，本地测不出来
- 这个配置缺失会直接非零退出，不会回退到默认值
- 父类/全局样式会覆盖这里的定义，得用更高优先级

**没有合格约束就写 `-`。**
「没看就写的 `S:-`」和「编造的 S」同样是错的——`S:-` 是在声明"我查过了，这里没有坑"。

## 四、配额上限（机器口径）

### 字段长度

| 字段 | 上限 |
|---|---|
| F | 160 字 |
| R | 360 字 / 最多 8 项 |
| A | 400 字 / 最多 6 项 |
| S | 按重要性分档，见下 |

### S 配额（按重要性）

| Importance | S 上限 |
|---|---|
| C9–C8 | 600 |
| C7–C4 | 200 |
| C3–C1 | 50 |

**token 怎么算**：UTF-8 字节数 ÷ 3。一个中日韩字符 = 1 token。
所以 50 rune 的 S 里，中文最多约 50 字（含标点）。

### 高重要性对象的额外义务

对 C6–C9 的对象，写 `S:-` 之前，先去"行为真正被决定的地方"找证据：

- 接口背后的实现
- 包裹它的切面或拦截器
- 它执行或供给的 SQL
- 模板与脚本
- 覆盖它的配置
- 持久化路径上的缓存、事务、软删、唯一性规则

找不到再由 `F`/`R`/`A` 推不出的重要约束，才写 `-`。

## 五、写法自检

写完一条，问自己三个问题：

1. **删掉这条，agent 会少知道什么？** 如果答案是"没什么"，说明这条是废话
2. **这条里有没有代码里明写的东西？** 有就删掉，那是浪费上下文
3. **S 真的不可推断吗？** 如果看一眼代码就知道，它不该进 S
